# Two-person username login

The active users are `tape` and `pat`. Supabase Auth still owns password hashing, sessions and JWT verification; financial tables still use auth.uid() and RLS. Usernames map to reserved internal aliases `tape@moneyspace.invalid` and `pat@moneyspace.invalid`. These are not mailboxes. The aliases are public identifiers, not credentials. Browser code has only the public publishable key.

The two users were created through Supabase Auth Admin createUser with email_confirm=true. No mail or invitation was sent. Generated initial passwords are in separate private handoff files outside the repository. They are never in source, migrations, GitHub, builds or browser storage. Sign in then use Change password; it verifies the current password before calling Auth updateUser({password}). No email/OTP flow is used. Passwords themselves are not stored in public application tables. Supabase Auth's encrypted_password field stores managed hashes.

A short-lived server-side provisioning function authenticated with a random 384-bit operator secret; unauthenticated invocation was verified as HTTP401. It used the server's existing service role environment, never exposed to the browser. After creating the two accounts it was replaced with an inert HTTP410 handler and JWT verification was re-enabled. There is no usable public provisioning endpoint. The bootstrap secret is no longer needed. No active admin credential was added to the repository.

Migration `close_public_account_registration` rejects auth.users INSERTs for every role except the managed postgres maintenance roles. This blocks public signup regardless of provider, while allowing existing users to sign in and change passwords. It also intentionally blocks future Admin createUser calls through the Auth server. An operator must explicitly modify/remove the guard for future account provisioning. Maintenance SQL access remains privileged. This is database-enforced signup closure; the Auth Dashboard's disable_signup setting is not claimed as modified. Disabling that setting in the Dashboard is optional defense in depth.

Validation: both real users signed in, updated to newly generated random passwords through Auth updateUser, re-signed in and signed out the verification sessions. Their handoff files were updated to the verified current passwords. The live signup endpoint was rejected before a new user was created; auth.users contains exactly the two intended accounts. Existing RLS authorization assertions passed. PostgreSQL CI separately models the supabase_auth_admin role to test the rejection trigger; the hosted managed postgres cannot SET ROLE to that protected role, so live verification uses the public Auth endpoint instead.

Manual review: open the site, sign in as each user, complete first-run setup, change initial passwords, sign out and sign in again. Wrong passwords must show a generic error; no register, magic-link or email-reset buttons should exist. Verify private account/category isolation. Real financial recording remains M3.

If a password is forgotten, there is no public reset or backdoor: a trusted project operator must use the Supabase Auth Admin updateUserById API to set a new random password and deliver it privately. Never disable RLS or put a service-role key in GitHub Pages to implement recovery. Old handoff files become obsolete after the users change passwords.
